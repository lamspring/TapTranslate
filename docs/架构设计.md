# 「翻译模式」架构设计（Android · 7 天 MVP）

> 一句话：静音 = 进入翻译模式 → 屏幕上任何系统渲染的文字可点 → 点词出翻译 + 虚线标记 → 手势完全不受影响。
> 目标：把"查一个词"从 ~5 秒压到 ~1 秒。
>
> **已拍板决策（2026-09-14）**：① 目标机 Android 16（API 36，远高于 minSdk 29）② 本地离线翻译为主 + 用户自带 LLM API Key 为自费引擎（Key 仅加密存本机）③ 仅完全静音（SILENT）开机，振动不算 ④ 悬浮小卡片（非弹窗、无发音、上下自动避让、上下文感知翻译优先 LLM 引擎）⑤ 默认词级，用户可切换短语级。

---

## 1. 技术选型：为什么是 Kotlin

| 候选 | 结论 | 理由 |
|---|---|---|
| **Kotlin（原生）** | ✅ 采用 | 无障碍服务、窗口管理、手势注入都是系统级 Java/Kotlin API；协程天然适合事件流；Google 官方一等语言 |
| Java | ❌ | 同能力但样板代码多，协程缺失 |
| Flutter / React Native | ❌ | 无法注册 `AccessibilityService` 系统组件、无法创建 overlay 窗口到别的应用之上——跨平台框架做不了系统级功能 |
| C / C++ (NDK) | ❌ | 本项目的性能瓶颈在 Binder 通信和翻译模型，不在 CPU 密集计算；NDK 只会增加复杂度 |
| Rust | ❌ | 同 NDK，过度工程 |

**关键决定：minSdk 29（Android 10）。**

原因：`AccessibilityNodeInfo.refreshWithExtraData(EXTRA_DATA_TEXT_CHARACTER_LOCATION_KEY)` 从 API 29 开始提供**逐字符的屏幕坐标矩形数组**。这是整个"点词判定"的免测量方案——没有它就得自己用 TextPaint 估算文字位置（需要对每种字体、行距做标定，7 天内必死）。目标机 Android 16 完全满足。

参考实现佐证：GitHub 上同类项目（[AidanPark/android-screen-translator](https://github.com/AidanPark/src-screen-translator)、[ciddwd/overlay-translator](https://github.com/ciddwd/overlay-translator)、[LinYiXin123/taotao-screen-translator--APP](https://github.com/LinYiXin123/taotao-screen-translator--APP)）全部是 **Kotlin + AccessibilityService + ML Kit 本地翻译** 栈，与我们选型一致。注意它们大多走 OCR 截图路线（为了覆盖游戏/视频文字——我们明确砍掉），我们的无障碍节点路线**更轻、更快、更省电**。

- 无障碍服务（用户在设置里手动开启，一次性）
- 无需 `SYSTEM_ALERT_WINDOW`——`TYPE_ACCESSIBILITY_OVERLAY` 窗口随无障碍服务自动获得，悬浮在应用之上

## 3. 核心机制逐条落地方案

### 3.1 触发：静音状态模拟开关（已拍板）

- `AudioManager` 三态：NORMAL / VIBRATE / **SILENT**
- 在 Service 里**动态注册** `RINGER_MODE_CHANGED_ACTION` 广播接收器（动态注册不受 Android 8+ 隐式广播限制，且以 `RECEIVER_NOT_EXPORTED` 注册满足 targetSdk 34+ 要求）
- **粒度约定：仅 `RINGER_MODE_SILENT`（完全静音）算开，振动（VIBRATE）不算**
- 技术债备注：这是模拟方案，正式版会换成自己的 Quick Settings 磁贴或音量键组合，Service 层接口预留好即可

### 3.2 交互：透明 overlay + 轻点/滑动区分

这是全项目最精妙也最容易踩坑的一环：

1. 模式 ON 时，Service 添加一个全屏 `TYPE_ACCESSIBILITY_OVERLAY` 窗口，content 是一个自定义 View。
2. View 的 `onTouchEvent` 里用 `ViewConfiguration.scaledTouchSlop` 做判定：
   - **ACTION_DOWN**：先 return true 占住事件流（保证能收到后续 MOVE/UP 做判定），同时清掉上一个卡片
   - 手指位移 **未超过 slop** 且 UP 及时 → 判定为**轻点** → 查词，不往下传（消费掉）
   - 位移**超过 slop** → 判定为**滑动** → 立即用 `AccessibilityService.dispatchGesture()` 把整条手势路径**原样回注**给底层 App（`GestureDescription.StrokeDescription` + `continueStroke` 流式续传）
3. 结果：App 收到的滚动/翻页/返回手势与 overlay 不存在时几乎一致（多一次 Binder 转发，毫秒级，人眼无感）
4. 边缘返回手势、通知栏下拉同理——本质是滑动手势，都会被正确回注

> ⚠️ 替代方案（不要用）：overlay 设 `FLAG_NOT_TOUCHABLE` 完全放行，靠 `TYPE_VIEW_CLICKED` 无障碍事件感知点击——该事件只有带点击监听器的控件才发，普通 TextView 不触发，覆盖率太低。

### 3.3 点击判定：词边界计算（免测量方案）

点击瞬间执行（总耗时预算 < 50ms）：

1. 从 `service.windows` 找到点击坐标所在的窗口 → `getRoot()` 拿到节点树
2. DFS 遍历，用 `node.getBoundsInScreen()` 做矩形命中，找到**最深的包含点击点的、text 非空的节点**
   - 整棵树遍历一次约几百个节点，协程后台线程执行，无感
   - **不做任何滚动状态缓存**——滚动发生后弹窗和虚线直接清掉，重新点重新算
3. 对该节点调用 `refreshWithExtraData(EXTRA_DATA_TEXT_CHARACTER_LOCATION_KEY, args)`，拿到**每个字符的 RectF**
4. 词边界算法：
   - 英文/空格语言：把连续的字符矩形合并成词矩形 → 命中测试点击落在哪个词
   - 中文：对整串字符做分词（见 3.4），把词内字符矩形合并 → 命中测试
5. 超长文本保护：单次 `refreshWithExtraData` 有长度上限（约 2 万字符），超长节点按 args 分段请求或降级为"整节点作为查询文本"

### 3.4 分词方案（已拍板：默认词级，用户可切短语级）

| 语言 | 方案 | 说明 |
|---|---|---|
| 英文 | 字母数字连续段切分 | 零依赖 |
| 中文 | **词典正向最大匹配（FMM）** | 生产版内置 5–8 万常用词词典（约 1–2 MB），纯 Kotlin 实现，单句分词 < 1ms。MVP 先内嵌微型词典跑通链路 |

**粒度（已拍板）**：默认词级；用户在设置中可切换"短语级"。
- 短语级 · 中文：词典长词优先匹配（词表含多字词/惯用语条目，最长匹配 12 字）
- 短语级 · 拉丁文：邻词合并启发式——相邻词间距小于行高 0.8 倍且最多合并 3 个词。MVP 启发式，随真实使用校准

为什么不调"返回逐词对齐的翻译 API"：Google Cloud Translation 的对齐能力对中文支持不稳定且要联网+Key+计费；本地 FMM 够用且零成本。

### 3.5 翻译：双引擎（已拍板）

**主引擎：ML Kit 本地翻译**
- `com.google.mlkit:translate`，英↔中模型首次使用时下载（约 30 MB/语言对），之后**完全离线、零费用**
- 单次词/短语翻译 **< 50ms**
- 局限：不知道上下文，一词多义时给出最常见义项

**自费引擎：用户自带 LLM API Key（OpenAI 兼容的 chat/completions 接口）**
- 用户在设置页填入 endpoint / model / apiKey，用自己的 Key 调自己的服务
- 核心优势：**上下文感知**——把"整句 + 被点词"一起发给 LLM，返回该词在当前语句链路中的恰当代入释义（这正是本地离线做不到的）
- Prompt 约定：只输出简短中文释义（≤30 字），temperature 0.2
- 引擎选择逻辑：LLM 三项配置齐全 → 用 LLM；否则回退 ML Kit

**统一接口**：`Translator.translate(word, contextSentence)`——词边界计算时同时提取被点词所在整句作为 contextSentence，两个引擎共用。本地引擎收到 context 也先忽略（接口预留）。

### 3.6 虚线标记与悬浮小卡片（已拍板：非弹窗，轻量悬浮卡，无发音）

- **悬浮小卡片**：overlay 内自绘（不开新窗口），锚定在被点词位置上方，占地面积极小（词 + 释义两行，宽度自适应、设上限）；点击位置距屏幕顶部不足"卡片高度 + 边距"时，自动翻转到词下方，确保完整显示；水平方向自动钳制在屏内
- 不带发音（已拍板）；点击卡片外任意处、发生滚动、模式关闭时消失
- 虚线：自定义 View 的 `onDraw` 用 `DashPathEffect` 画在词矩形下缘（下移 2–3px）
- 明确不做整屏预渲染——与砍掉的第①条一致

### 3.7 LLM API Key 本地安全存储（已拍板）

- 主密钥存 **Android Keystore**（硬件级，不可导出）：AES-256/GCM，`KeyGenParameterSpec` 生成，私钥永不离开安全环境
- 用户的 API Key 用主密钥加密后（12 字节 IV + 密文，Base64）存入 App 私有 `SharedPreferences`；使用时解密仅在内存，**绝不写日志、绝不外传**
- 预留 `setUserAuthenticationRequired(true)` 开关：开启后每次使用 Key 需指纹/人脸验证（第二阶段加）

## 4. 性能与流畅性设计（不占手机性能的底气）

| 手段 | 效果 |
|---|---|
| **运行时动态改订阅**：`service.setServiceInfo()` 在模式 OFF 时只订阅最少事件（几乎零开销），模式 ON 才全开 | 模式关闭时 ≈ 普通前台应用的成本，24 小时挂着无感 |
| 点击时才计算词边界（用户规格即如此） | 零常驻计算 |
| 滚动/翻页时不做任何节点遍历（只监听滚动事件来清除弹窗和虚线） | 滚动帧率零影响 |
| 触摸事件透传走原生 `onTouchEvent`，滑动回注走系统 `dispatchGesture` | 主线程每帧只做轻量几何判定 |
| ML Kit 模型常驻内存（约 40 MB）只在模式 ON 时加载，OFF 时释放 | 内存可控 |
| 中文词典按需加载，懒初始化 | 冷启动 < 300ms |

## 5. 砍掉项的技术确认（与你的清单一致）

| 砍掉项 | 技术原因确认 |
|---|---|
| 整屏预加虚线 | N 个节点 × refreshWithExtraData 每帧调用 = Binder 风暴，必然掉帧 |
| 整屏双语渲染 | 需要重绘其他 App 的 View 树，非系统签名应用做不到 |
| 游戏/视频文字 | 那是像素不是文本节点，只能 OCR 路线（已明确排除） |
| iOS | 系统不允许全局无障碍读屏+悬浮窗组合 |
| 生词本/账号/付费 | 范围控制，接口预留 |

**当前进度：D1–D5 已完成并真机验证（OnePlus 11 · Android 16 · ColorOS）。** 端到端链路（点词 → 节点命中 → 空格分词 → ML Kit 离线翻译 → 虚线 + 悬浮卡片）已跑通；手势回注可滚动不崩溃。

**真机踩坑记录（勿回退）**：
1. 服务配置 XML 属性名是 `android:accessibilityFlags`，不是 `android:flags`
2. Kotlin 对 `GestureResultCallback`（抽象类）不能 SAM 转换，须 `object : ...`
3. 常量真名 `EXTRA_DATA_TEXT_CHARACTER_LOCATION_ARG_START_INDEX`（还有 `ARG_MAX_LENGTH`）
4. ColorOS 给 ACCESSIBILITY_OVERLAY 内容施加状态栏 insets：视图 `getLocationOnScreen` 的 loc=(0,139)。**触摸事件入口 +loc 换算、onDraw 必须 -loc**（写反会把虚线/卡片画到 2×139px 下方——这就是"虚线出现在空行"的根因）
5. **dispatchGesture 回环（滑动失灵的真正根因）**：回注手势作为新事件流派发时会弹回最顶层的可触摸窗口——即我们自己的 overlay——形成 begin→回注→begin 的无限回环，底层 App 收到一堆碎手势、页面永远不滚。且 `updateViewLayout` 改 FLAG_NOT_TOUCHABLE 的传播速度追不上回注注入速度，边转发边改标志必然 race。**最终方案：累积+延迟一次回注**——越过 touchSlop 时立即设 NOT_TOUCHABLE（给 WMS 传播留出整个滑动时长），滑动期间只记录路径点，原始手势 UP 时才把完整路径作为单段手势 dispatchGesture；回注完成（onCompleted/onCancelled）后才恢复可触摸，并短暂屏蔽点击防尾段弹回造成幽灵点词
6. `service.windows` 可能先命中自家 overlay → 只选 `TYPE_APPLICATION` 窗口
7. `StaticLayout.width` 返回构造时传入的布局宽度而非文字实际宽度 → 卡片定宽必须用每行 `getLineWidth(i)` 累加
8. 无障碍事件风暴（网页懒加载刷 WINDOWS_CHANGED）会秒清卡片 → 只在 `TYPE_VIEW_SCROLLED` 时清除

验收标准（对应你的交付物）：自己手机上每天真用 → 能点词 ✓ 出翻译 ✓ 手势不冲突 ✓

## 7. 风险与备案

1. **字符坐标失效场景**：部分 App（自绘 View、部分 Compose 自定义节点）不返回字符坐标 → 降级：拿节点整段文本做查询，卡片锚定节点矩形
2. **WebView 撒谎（夸克）**：夸克等浏览器不暴露网页文字，整个 WebView 节点只有标语 text（'夸克-新生代智能搜索'），且对逐字符坐标请求返回**与节点整边界相同的常量矩形**（10 个字符全部=全屏矩形）——据此切词会把整节点当一个词，画出全屏宽虚线、翻译出"夸夸"这种垃圾。已加检测：`charRects` 几乎全部相同或等于节点边界时判为不可信；WebView 类节点不可信→按未识别处理并提示"该应用未暴露网页文字"。**浏览器实测：夸克不暴露（永远不会）；OPPO 自带浏览器能力时好时坏；Chrome 全链路验证通过**（AI 概览 View 节点与正文 TextView 节点均返回真实逐字符坐标：centuries/during/English 精确命中、虚线落词准、滑动回注正常）。**注意"新会话相关性"**：浏览器坐标服务在无障碍服务实例较新时稳定提供，使用一段时间后可能"存根化"（refresh 返回 true、extras 恒 null，重试/重走树/切后台/强杀均不恢复）；若点词退化为整段翻译，拨动静音开关重启模式或重启手机可恢复。后续可考虑检测连续存根后自动重置服务状态
3. **ML Kit 孤立词多义词失真**：离线引擎逐词翻译无上下文，如 "away"→"距离酒店"（应为"离开/远离"）；Practice→实践、language→语言 正常。对策：LLM 自费引擎（已留接口）或对 ML Kit 传入整句做对照（后续版本）
4. **手势回注的边界情况**：极少数 App 对 `dispatchGesture` 注入的滑动敏感（如全屏手势短视频）→ 备案：这些 App 包名加入白名单，模式下自动不覆盖
5. **回注手感**：延迟一次回注意味着滑动在抬手时才整体回放给底层 App，路径和总时长一致但**没有挥动速度（fling）**，快速甩动只会匀速滚动不惯性滑行；连续滑动时第二次起的手势会直接穿透 overlay 原生滚动（反而更顺）。若后续要惯性，可改为定时分块回注（首块仍可能 race，需配合弹回检测）
6. **短语级粒度是启发式**：拉丁文邻词合并在部分语境会切错边界 → MVP 接受，收集真实用例后换词典/规则
7. **误触率**：卡片位置与下一次点击的关系需要 D6 真实使用校准
